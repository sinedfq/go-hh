# Подготовка проверки телефона и SMS

## Вход на сайте и интерфейс кода

На сайте можно выбрать «Почта» или «Телефон». `POST /api/auth/phone/web/request`
принимает номер и случайный секрет текущей формы браузера. Код отправляется
через Firebase только на устройства, ранее зарегистрированные авторизованным
владельцем номера. Токен получателя из браузера не принимается. Пользователь
вводит код из уведомления приложения, подтверждает его и завершает вход.
Для этого необходимо заранее привязать номер в приложении и войти на телефоне.

Миграция `030_web_phone_login.sql` закрепляет за запросом владельца аккаунта.
Если номер перепривязали к другому аккаунту, прежний код не откроет новый аккаунт.
Подтверждение веб-входа нельзя использовать для регистрации или привязки номера.
Секрет браузерной формы хранится только в памяти; после перезагрузки нужен новый код.

Телефон форматируется как `+7 (999) 123-45-67`; международные коды сохраняются.
OTP отображается шестью блоками с поддержкой вставки целого кода, удаления и
зелёной подсветкой подтверждённого значения. В Android выбор способа входа
оформлен переключателем «Почта / Телефон».

Переключатели событий доступны и при выключенном общем переключателе.
Запреты Android показываются отдельно со ссылками на соответствующие каналы.
Выключение событий подавляет их отображение локально; авторизованное устройство
остаётся зарегистрированным для запрошенных пользователем кодов входа.
При выходе из аккаунта токен устройства удаляется с сервера.

## Firebase и привязка номера (27.10.2026)

Текущий локальный режим — `OTP_MODE=firebase`, `APP_ENV=development`.
Обычные уведомления сообщений и событий также работают через Firebase;
коды используют отдельный канал «Коды подтверждения». Настройки уведомлений
и документов перенесены на отдельные экраны. В «Настройки → Телефон» можно
привязать номер к существующему аккаунту или заменить его после подтверждения.

В запросе кода Android передаёт `push_token` Firebase и случайный `request_id`,
помимо `phone` и `device_key`. Сервер отправляет код через FCM data-message;
`development_code` в HTTP-ответ не попадает. Приложение принимает только
ожидаемый запрос, проверяет срок действия и удаляет уведомление после проверки.
При ошибке FCM запрос отклоняется, недоставленный код удаляется.

`GET /api/account/phone` возвращает номер текущего пользователя.
`PUT /api/account/phone` принимает `phone`, `phone_receipt`, `device_key`;
привязка и погашение подтверждения выполняются атомарно. Оба маршрута требуют
обычной авторизованной сессии. Номер другого аккаунта привязать нельзя.

Это всё ещё тестовая проверка установки приложения, а не владения SIM-картой.
Тестовый вход по телефону сохраняет ограничение на устройство регистрации или
привязки. Почта/пароль работают на другом устройстве. Для настоящей проверки
владения номером нужен SMS-провайдер либо отдельная интеграция Firebase Phone Auth.

`scripts/api.ps1 -RequirePush` проверяет порт до старта: работающий API с Firebase
используется повторно, посторонний процесс не завершается. Для второго экземпляра
можно задать другой `HTTP_ADDR`, например `:8082`.

## Мобильный сценарий (обновление 27.10.2026)

В Android добавлены телефон при регистрации, запрос/проверка кода и вход по
телефону. Мобильная регистрация использует `POST /api/auth/mobile/register`:
`email`, `password`, `role`, `phone`, `phone_receipt`, `device_key`. Телефон и
погашение подтверждения сохраняются в одной транзакции с созданием аккаунта.
Повторный номер отклоняется без создания лишнего пользователя.

`POST /api/auth/phone-login` принимает `phone`, `phone_receipt`, `device_key`
и возвращает обычную сессию после проверки подтверждения. Миграция
`029_mobile_phone_accounts.sql` хранит привязку номера отдельно от старых аккаунтов.

Для временной доставки установите `APP_ENV=development`,
`OTP_MODE=app_notification` и отдельный `OTP_SECRET`. Этот режим принимает
введённый номер, возвращает код только запросившему приложению, а Android
показывает системное уведомление «Тестовый код Trudomix». Коды скрыты на
заблокированном экране, не передаются на другие устройства уведомлениями,
удаляются после проверки и автоматически истекают. Это не реальная SMS-проверка.

`device_key` — случайный секрет установки. Он не попадает в резервное копирование
Android. Запрос и проверка кода связаны с ним; тестовый вход разрешён только
на устройстве регистрации. Тестовый код не открывает аккаунт, созданный с
проверкой через настоящие SMS. При переустановке или смене устройства доступен
вход по почте и паролю. Секрет режима следует сохранять между перезапусками.

Для локального запуска `scripts/api.ps1` и `scripts/stack.ps1` читают необязательный
`.cache/otp.local.json` с `mode: "app_notification"` и `secret`. Файл исключён из Git.
В production режим уведомлений не включается. Сборки CI также не получают
локальный секрет и по умолчанию оставляют OTP выключенным.

Уведомления кода запрашиваются пользователем отдельно от необязательных
уведомлений о событиях. Запрет Android или отключённый канал требуют разрешения
в настройках устройства; код не выводится обходным способом в форме.

Ниже сохранено описание базового сервиса; этап мобильной интеграции выше уже выполнен.

Базовый сервис проверки номера выдаёт одноразовое подтверждение. Само по себе
оно не является сессией; мобильная регистрация и вход по телефону обменивают его
на обычный токен аккаунта после серверных проверок. Веб-вход по почте сохранён.

## Режимы

По умолчанию `OTP_MODE=off`, API конфигурации возвращает `enabled: false`.
Миграция `028_phone_verification.sql` добавляет отдельную таблицу и не меняет
аккаунты, пароли, резюме и существующие сессии.

Для локальной проверки задайте в своём, исключённом из Git, `.env`:

```dotenv
APP_ENV=development
OTP_MODE=development
OTP_SECRET=<отдельный случайный секрет не короче 32 байт>
OTP_TEST_PHONES=+79990000001
```

Секрет должен отличаться от `JWT_SECRET`. Для генерации:
`node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`.
Секреты не помещаются в Git, клиентские приложения или ответы API.

Примените миграции и пересоберите API обычным скриптом запуска Docker-стека.
В development-режиме SMS не отправляются: шестизначный код возвращается
в `development_code` только для номеров из явного списка `OTP_TEST_PHONES`.
Запуск этого режима с `APP_ENV=production` завершается ошибкой конфигурации.

Проверка полного тестового цикла без вывода кода и подтверждения в терминал:

```powershell
node scripts/phone-otp-check.mjs http://localhost:3000 +79990000001
```

Скрипт отказывается работать с реальной SMS-доставкой. Повторять запрос можно
через 60 секунд; действует также часовой лимит.

## API

- `GET /api/phone-verification/config` — `enabled`, `test_mode`.
- `POST /api/phone-verification/request` с `{ "phone": "+79990000001" }` —
  `challenge_id`, `expires_in` (300 секунд), `retry_after` (60 секунд).
- `POST /api/phone-verification/verify` с `challenge_id` и `code` —
  `verified`, `verification_receipt`, `expires_in` (600 секунд).

Номер нормализуется: российский `8 (999) 123-45-67` становится `+79991234567`;
международные номера вводятся с `+` и кодом страны. Локальный номер без кода
страны не угадывается. Техническая проверка формата не подтверждает выдачу
номера оператором связи.

Подтверждение — непрозрачное одноразовое значение. При дальнейшем подключении
аккаунтов сервер использует `Service.Redeem`, проверяет срок и погашает его один
раз; клиенту нельзя доверять флагу `verified` без серверной проверки. Для операции
с аккаунтом погашение нужно включить в ту же транзакцию. Подтверждение номера
не является JWT и не принимается как вход в аккаунт.

## Подключаемый SMS-провайдер

Контракт — интерфейс `phoneotp.Sender`. Готов HTTP-адаптер шлюза:

```dotenv
APP_ENV=production
OTP_MODE=http
OTP_SECRET=<отдельный секрет>
SMS_GATEWAY_URL=https://your-sms-gateway.example/send
SMS_GATEWAY_TOKEN=<токен шлюза>
```

Это адрес адаптера к выбранному поставщику, а не обещание совместимости
с произвольным SMS API. После выбора поставщика реализуется его формат
или шлюз, принимающий `POST` JSON `{phone, code, expires_in}` и возвращающий
2xx только при принятии сообщения к доставке. Токен передаётся как Bearer,
не в URL. Перенаправления запрещены. Дедлайн отправки — 8 секунд;
внешние ошибки и содержимое ответа провайдера не выводятся пользователю.
Незашифрованный HTTP допустим только для loopback-тестов в development.

## Ограничения и хранение

Код действует 5 минут, допускается 5 попыток. На номер — не более 5 запросов
за час и пауза 60 секунд, на IP соединения — 30 запросов за час. Ограничения
и счётчики хранятся в PostgreSQL и сохраняются после перезапуска API.
Конкурентные проверки и погашения сериализованы. Неудачная доставка не выдаёт
рабочего подтверждения и не сбрасывает ограничения отправки.

Коды, подтверждения и IP хранятся в виде HMAC с разными областями применения;
сам номер необходим для доставки и ограничения повторов. Записи старше суток
с истёкшим сроком удаляются небольшими партиями при следующих запросах.
На неактивном сервисе для гарантированного срока удаления следует настроить
отдельную периодическую очистку.

`X-Forwarded-For` не считается доверенным: за общим прокси лимит IP относится
к соединению прокси. Перед включением реальной доставки следует согласовать
доверенные прокси и ограничения расходов с выбранным SMS-поставщиком.

Следующие этапы — настоящая доставка через выбранного SMS-поставщика, формы
телефона на вебе и привязка номера для ранее созданных аккаунтов. В Android
регистрация и вход уже подключены; после смены установки тестовый аккаунт
доступен по почте и паролю.
